0. Read this first

0.1 What this application is

Dr. Pooja's Physio is a physiotherapy practice run mostly online. The website sells and delivers physiotherapy in two ways:

  • Video consultation (online) — the patient books a slot, pays, and joins a Google Meet video call at the appointed time.
  • Home visit — a physiotherapist travels to the patient's home. The patient's pincode must be inside an admin-configured service area, and a travel fee is added on top of the price.

Around that sit five things you will test:

  1. A public marketing website of eight pages that explains the practice and funnels visitors into booking.
  2. A patient portal: book, pay, see sessions, buy multi-session packages, keep a health profile, upload scan reports, cancel and get refunds.
  3. A therapist portal: set weekly availability, run sessions, write clinical records (triage, health profile, pain map, session notes), see earnings and request payouts.
  4. An admin back office with six sections (Today, Sessions, People, Money, Catalog, Settings) that runs everything — approvals, assignment, catalog, pricing, refunds, payouts and every product setting.
  5. A hospital (partner) portal: refer patients to the clinic and earn a share of the revenue those patients generate.

0.4 The debug bar (your main tool)

Every page of this application currently shows a black Debug bar pinned to the very top of the screen. It exists only before launch and carries three controls:

ControlWhat it doesHow to use it
Jump to page (dropdown)Navigates straight to any route, including protected dashboards.Click the dropdown, pick e.g. "14b. Admin Dashboard (protected)".
Simulate now (date/time field + Set)Moves the browser's idea of "now" forward or backward, so time-gated features can be tested without waiting.Click the field, type/pick a date & time, click Set. The page reloads and runs on the simulated clock. Click Reset to Real Time to undo.
Reset dataEmpties every table and deletes every non-admin account.See step 1 below.

Important limitation of the simulated clock — read this or you will file false bugs. The simulated clock is a browser-side override only. It changes what the following surfaces believe the time is:

  • the date/time picker in both booking wizards (which dates and hours are offered),
  • the Tap to Join button (when it opens, and when it turns into Session Completed),
  • the therapist-suggested-session cards (when a suggestion stops being acceptable).

It does not change the server's clock. Refund eligibility, payout maths, package expiry sweeps and the server-side lead-time re-check all use the real server time. So: jumping the clock forward to make a session look joinable is fine and expected. Jumping the clock backward to book a slot that is really only 2 hours away will be rejected by the server — that is correct behaviour, not a bug.

0.5 STEP 1 — Reset all data (do this once, before anything else)

The plan below assumes an empty database, so that counts, lists and money figures start from zero and every expected result is exact.

  1. Open [SITE] in Chrome.
  2. In the black Debug bar at the top, click Reset data (it may read Empty the database, keeping admin accounts).
  3. A confirmation field appears. Type exactly RESET ALL DATA (capital letters, one space between words).
  4. Click Reset.
Expected result: the button shows "Resetting…", then the page refreshes. Every patient, therapist, hospital, booking, payment, package, health record and setting change is gone; admin logins still work; all product settings are back to their factory defaults (listed in section 0.8). If you instead see "Reset is switched off on this server (ALLOW_DEBUG_DATA_RESET is not set)", stop and ask the owner to set that server variable — do not continue, because leftover data will make later expected results wrong.
If you are testing on an environment where the reset button is intentionally disabled, you can still run the plan, but treat every "the list is empty" expectation as "your new row appears at the top of the list".

Each test case below has an ID, a persona (who is signed in), a precondition, numbered steps, and an expected result. Do the steps in order. Compare what you see against the expected result literally: if the expected result says the button reads "Review Booking →" and it reads "Next", that is a bug.

2.3 Booking a single video session (the booking wizard)

What this is — read before testing. /book is a three-step wizard:

  • Step 1 — When. A calendar of bookable dates, a row of time chips for the chosen date, and a row of language chips. The wizard pre-picks the earliest legal date, the earliest legal hour and the first language, so the step is complete on arrival; each pre-pick is highlighted once until the patient chooses for themselves. Only slots at least [online booking lead time] hours ahead are offered (12 by default, set in Settings → Booking Rules).
  • Step 2 — Who and what. If signed out: full name, email, password, phone, confirm password and an optional referral code — this creates the account. If signed in, it just says "Booking as …". Admin settings that change this screen: online booking lead time, booking languages, online cancellation refund window, treatment categories (which options exist and at what price), session packages visible (for ?package= links).

5.2 Money → Summary and the two identities

What this is. Every figure on Money comes out of one calculation, so the strip, the cards and the chart can never disagree. Two identities must always hold:
